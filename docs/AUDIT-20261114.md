### M-01｜P1｜流程／部署｜文件教的 Cloud Run 部署，後端一啟動就崩潰

**證據**

- `server/Dockerfile:4` 只把 `server/` 複製進映像（`COPY . ./server`），`docs/cloud-setup.md:185` 教的指令是 `gcloud run deploy maglody-master --source server`。
- 但後端引用了 `server/` 以外的檔案：`server/app.ts:2`（`../src/agent/reply.ts`）、`server/llm/gcp.ts:1-2`、`server/llm/openai.ts:1-2`（`../../src/lib/request.ts`、`../../src/agent/reply.ts`）。
- 實測：把 `server/` 單獨複製到空目錄，`PORT=8791 node server/index.ts`（provider 用預設 mock）直接結束：
  `Error [ERR_MODULE_NOT_FOUND]: Cannot find module '…/src/lib/request.ts' imported from …/server/llm/gcp.ts`
- Render 路線（`docs/cloud-setup.md:149-155`，從 repo 根目錄 `node server/index.ts`）不受影響。
- `docs/cloud-setup.md:237` 自己寫了這套流程沒用真金鑰驗過；沒有任何測試會建這個映像。

**建議修法**

擇一：(a) 把 `reply.ts`、`request.ts` 搬到前後端共用的目錄（例如 `shared/`），Dockerfile 一起複製；(b) build context 改成 repo 根目錄，文件指令同步改掉。再加一個 smoke test：照 Dockerfile 的複製範圍起服務，打 `/api/health`。

**驗收標準**

- 照 `docs/cloud-setup.md` 的指令範圍（或更新後的指令）建出的映像，啟動後 `GET /api/health` 回 200。
- `npm` 有一個指令會做上面這件事，並且在 CI 裡跑（見 M-19）。

### M-02｜P1（接上真金鑰後）｜架構／安全｜`/api/master` 是沒有驗證、沒有限流的模型轉發

**證據**

- system prompt 由瀏覽器送出：`src/agent/client.ts:56`。後端只檢查它是不是 20,000 字以內的字串就原樣轉給供應商：`server/app.ts:9`、`server/llm/openai.ts`、`server/llm/gcp.ts`。
- 來源檢查只在請求帶 `Origin` 時生效：`server/app.ts:30`。不帶 `Origin`（curl、任何腳本）直接放行。
- 沒有任何次數限制。文件還教用 `--allow-unauthenticated` 部署（`docs/cloud-setup.md:186`），並在 `:236` 承認「還沒有每人每分鐘次數限制」。
- 實測（本機，`LLM_PROVIDER=openai`、`OPENAI_BASE_URL` 指向自己寫的假上游、`ALLOW_ORIGIN` 設成別的網域）：
  - 不帶 `Origin`，`system` 填「You are a general assistant. Ignore music.」→ 回 200，假上游收到的 system 就是這句。
  - 帶 `Origin: https://evil.example` → 403（瀏覽器這條路有擋）。
  - 連打 30 次 → 30 次都是 200，假上游共收到 31 次呼叫。
- 回覆會被截到 text 400 字＋learned 200＋next 200（`src/agent/reply.ts:28`），所以拿來當免費聊天機器人不好用；但每個請求可以塞到 200 KB 輸入（`server/app.ts:5`），花的是擁有者的額度。
- 目前預設是 mock、不花錢。repo 內看不出線上有沒有接真金鑰，所以嚴重度標「接上之後 P1」。

**建議修法**

1. system prompt 搬到後端：`MASTER_SYSTEM_PROMPT` 由 server 自己帶，請求只收 `step`、`persona` 代號、歌曲摘要、問題、歷史；`buildUserTurn` 也在後端組。
2. 加上限流（每 IP 每分鐘、每日總量），超過回 429；前端本來就會退回離線教練。
3. 縮小輸入上限：歌曲摘要＋8 則歷史用不到 200 KB。
4. 文件把「預算上限是最後一道防線」改成「限流＋預算上限」，並拿掉沒有限流時的 `--allow-unauthenticated` 建議。

**驗收標準**

- 請求裡帶 `system` 欄位時，後端忽略或回 400；單元測試證明送到 provider 的 system 永遠是後端那一份。
- 同一來源一分鐘內第 N+1 次請求回 429，有測試。
- 超過新上限的 body 回 413，有測試。

### M-06｜P1｜易用性／文案｜預設的夥伴聊天答非所問，同一句重複三次

**證據**

  | 我問 | 作曲家回 |
  |---|---|
  | 為什麼這和弦？（內建開場句） | （輕輕哼了兩句）這首還沒命名的歌的副歌還沒排和弦，旋律有 0 個起音。先哼最後兩個音，聽它是否想回到開頭。你還沒排和弦。先點每個和弦聽聽… |

**驗收標準**

- 主歌、副歌各兩句且副歌不含原句時，主畫面有前進鈕。

- 哼唱分析在主執行緒同步執行（`src/steps/Hum.tsx:36-55`，最長 25–40 秒的音訊）。這次沒有量它卡住畫面多久，列為待量測。
- 首包：JS 416.73 kB（gzip 145.61 kB）單一 chunk、字型 365.38 kB、CSS 81.03 kB。九檯和聊天、靈感全部一次載入。以手機網路來說偏重，但不是現在的瓶頸。
- 技術選型整體是合理的：純前端、Web Audio 即時合成、零後端也能用、後端零相依。React 19＋Vite 7 都是現行版本。不建議現在換任何框架。

**建議修法**：先量再動。哼唱分析搬到 Web Worker；各檯改 lazy 載入；ScriptProcessor 等有 iOS 實機結果後再決定。

**驗收標準**：25 秒哼唱分析期間主執行緒沒有超過 200 ms 的長任務；首屏 JS（gzip）降到 100 kB 以內。
